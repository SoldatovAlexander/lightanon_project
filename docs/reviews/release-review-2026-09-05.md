В продукте есть воспроизводимые сценарии выхода исходных данных, обхода проверки зашифрованного хранилища и восстановления ранее удалённых записей. Предыдущее заявление о полном закрытии аудита было слишком сильным: полезные исправления внесены, но некоторые гарантии реализованы лишь частично.

P1 означает блокер production-релиза для соответствующего сценария. P2 означает дефект корректности или интеграции, который следует исправить до следующего публичного релиза либо явно ограничить поддерживаемый сценарий. P0 по выполненным проверкам не установлен.

Проверка охватила табличный Engine, StreamEngine, правила, RAG, vault, CLI, тесты, упаковку и примеры. Все проверки выполнялись локально с синтетическими данными и временными файлами. Код продукта не изменялся.

Результаты: `96 passed` при `.venv/bin/python -m pytest -q`; `pip check` не обнаружил конфликтов установленных зависимостей. Дополнительные воспроизведения выявили дефекты, отсутствующие в штатных тестах. `rag-demo.py` завершился с `AssertionError`. Матрица Python/ОС, сборка и установка wheel в чистом окружении, внешний анализ уязвимостей зависимостей и повторный юридический аудит не выполнялись.

## Подтверждённые замечания

### R01. P1: ошибка YAML-схемы оставляет исходные данные в результате

Код: [cli.py:25](../../lightanon/cli.py#L25), [cli.py:39](../../lightanon/cli.py#L39), [cli.py:312](../../lightanon/cli.py#L312).

`load_schema()` пропускает неизвестный метод, отсутствие `method` и неверную форму записи с предупреждением. Пропущенная колонка не попадает в audit_log. CLI затем сохраняет её исходные значения и завершается успешно. Исправление fail-closed в Engine этого не покрывает.

Воспроизведение: CSV `email\nreview@example.com\n`, схема `email: {method: Hahs}`. CLI завершается без ошибки, а выходной CSV содержит `review@example.com`. Если ошибочна только одна запись большой схемы, остальные правила отрабатывают и маскируют проблему.

Решение: проверять всю схему до чтения данных; использовать явный реестр допустимых классов вместо `hasattr/getattr`; проверять тип `params` и аргументы конструктора. Любая ошибочная запись должна прерывать запуск с ненулевым кодом до создания результата. Пустую схему разрешать только отдельной явной настройкой, если копирование действительно нужно продукту.

Приёмка: неизвестный метод, отсутствующий `method`, не-dict запись и частично ошибочная схема завершаются ошибкой; новый output не появляется, существующий output не меняется.

### R02. P1: заданный ключ не требует зашифрованного содержимого vault

Код: [vault.py:182](../../lightanon/rag/vault.py#L182), особенно проверка префикса на строке 187.

Fernet-проверка выполняется лишь для файлов с префиксом `gAAAA`. При переданном `encryption_key` обычный JSON принимается без проверки подлинности. При возможности подменить файл можно заменить зашифрованный vault JSON-маппингом и заставить приложение восстановить подставленное значение без знания ключа. Это дефект выбора формата, а не криптографии Fernet.

Подтверждено также, что открытие старого JSON с ключом не шифрует его. Если `sanitize` только переиспользует существующее значение, запись не выполняется и исходные данные остаются на диске открытыми, несмотря на ключ в настройках запуска.

Решение: при заданном ключе всегда требовать проверяемый зашифрованный формат; plaintext в таком режиме отклонять. Для совместимости добавить отдельную операцию миграции JSON -> encrypted vault с явными исходным и целевым путями, атомарной записью и проверкой результата. Формат определить версионированным контейнером, а не эвристикой префикса. Пустой существующий файл считать повреждением, если это не явно разрешённое создание нового vault.

Приёмка: plaintext с ключом отклоняется; неверный ключ и изменённый ciphertext не принимаются; миграция сохраняет все записи и удаляет plaintext из целевого файла даже без появления новых значений.

### R03. P1: несколько экземпляров FileVault теряют записи и возвращают удалённые данные

Код: [vault.py:153](../../lightanon/rag/vault.py#L153), [vault.py:262](../../lightanon/rag/vault.py#L262), [vault.py:310](../../lightanon/rag/vault.py#L310).

Каждый экземпляр загружает собственный снимок файла один раз и при изменении полностью сохраняет его. Атомарный `os.replace()` защищает от частичной записи, но не от устаревшего снимка.

Воспроизведение без параллельных потоков: A сохраняет email; B открывает тот же файл; A удаляет email; B сохраняет другое значение. Повторное открытие файла снова возвращает удалённый email. Аналогично последняя запись может стереть новые токены другого экземпляра. Это влияет на удаление ПД, TTL и восстановление ответа.

Решение для текущего FileVault: межпроцессная блокировка отдельного lock-файла и операция read-modify-write под ней, включая удаление, purge и проверки конфликтов. Блокировать нужно весь цикл, а не только `replace`. Для многопользовательского сервиса предпочтителен отдельный транзакционный backend с уникальными ограничениями. До его появления запретить конкурентные writers явно, если корректную блокировку нельзя обеспечить на поддерживаемых платформах.

Приёмка: два экземпляра и два процесса не теряют записи и не возвращают удалённые; такой же тест выполняется для encrypted vault. Добавить проверку удаления и записи в разном порядке.

### R04. P1: повторное использование значения теряет его тип и влияет на разрешение раскрытия

Код: [sanitizer.py:180](../../lightanon/rag/sanitizer.py#L180), [sanitizer.py:433](../../lightanon/rag/sanitizer.py#L433).

Поиск существующего токена выполняется только по исходной строке. Тип новой сущности не учитывается, а `restore_allowed_only` доверяет типу из имени ранее созданного токена.

Воспроизведение: первый sanitizer с custom rule `PUBLIC` сохраняет `review@example.com`; второй sanitizer с EMAIL-правилом и тем же vault получает для email токен `PUBLIC`. Политика, разрешающая только `PUBLIC`, восстанавливает этот email. Обратный порядок даёт неправильные маски и неожиданно запрещает восстановление.

Решение: ключ поиска должен включать минимум `(entity_type, value)`, а для общего хранилища нескольких клиентов также namespace/tenant. Хранить тип в записи vault и проверять его при раскрытии. Для legacy-записей тип извлекать при контролируемой миграции; несовпадение типа не должно молча наследовать старый токен.

Приёмка: одинаковая строка под разными типами получает независимые записи; чужой тип не проходит allowed-types; одинаковые тип и значение внутри namespace по-прежнему дедуплицируются.

### R05. P1: обычные форматы ПД пропускаются, а отчёт показывает низкий остаточный риск

Код: [patterns.py:14](../../lightanon/rag/patterns.py#L14), [patterns.py:69](../../lightanon/rag/patterns.py#L69), [patterns.py:142](../../lightanon/rag/patterns.py#L142), [patterns.py:148](../../lightanon/rag/patterns.py#L148), [sanitizer.py:255](../../lightanon/rag/sanitizer.py#L255).

Подтверждённые примеры для встроенных профилей:

| Вход | Текущее поведение |
| --- | --- |
| `ИВАНОВ ИВАН ИВАНОВИЧ` | Полностью остаётся открытым |
| `И. И. Иванов` | Полностью остаётся открытым |
| `Иванова-Петрова Анна Сергеевна` | Префикс `Иванова-` остаётся открытым |
| `Логин: ivan_dev` | Не распознаётся из-за регистра метки |
| `Карта 378282246310005` | 15-значный номер остаётся открытым |
| `ИНН 1234 5678 9012` | Разделённый пробелами идентификатор остаётся открытым |
| `Телефон: 79991234567` | Классифицируется как SNILS, а не PHONE |

После каждого примера `sanitize_with_report()` сообщает `residual_risk='low'`: остаточная проверка использует те же детекторы, поэтому не видит их собственных пропусков. Неправильный тип также влияет на `restore_allowed_only`.

Решение: сначала зафиксировать корпус этих строк и отрицательных примеров. Ввести контекстные детекторы меток документов и телефона с приоритетом над общими числовыми паттернами. Поддержать регистр меток, инициалы в обе стороны, составные фамилии и варианты группировки. Не нормализовать весь текст с потерей координат: детектор должен возвращать span исходного ввода. Для ФИО предусмотреть подключаемый NER-детектор, если измерения на целевом корпусе покажут недостаточность правил. Контрольные суммы использовать как дополнительный сигнал, чтобы опечатка в документе не превращалась в пропуск.

Поле отчёта заменить на честные показатели: `detected_count`, `residual_detected_count`, активные правила и предупреждение о неполноте покрытия. `0 найдено` не должно автоматически означать `низкий риск` или разрешение отправки в облако.

Приёмка: перечисленные значения скрываются целиком и получают правильный тип; отрицательный корпус проверяет обычные числа и текст. Отчёт явно отличает отсутствие совпадений от подтверждённого отсутствия ПД.

### R06. P1 для корпоративного сценария: бизнес-режим не обеспечивает заявленное разделение компании и контрагентов

Код: [sanitizer.py:135](../../lightanon/rag/sanitizer.py#L135), [patterns.py:117](../../lightanon/rag/patterns.py#L117), [patterns.py:127](../../lightanon/rag/patterns.py#L127), [patterns.py:133](../../lightanon/rag/patterns.py#L133).

`company` включает общие regex для всех организаций. Поэтому строка `Контрагент: ООО "Вектор", ИНН 7708123456, КПП 770801001.` обезличивается и в режиме `company`. В `company_and_counterparties` меняется главным образом группировка токенов. Система не знает, какая организация собственная.

Одновременно `ООО "Ромашка". Ромашка поставляет товары.` оставляет второе название открытым; `ООО "Я"`, `Юридический адрес: Москва` и `ОГРНИП 304770000000001` не скрываются. Неквотированное `ООО Ромашка поставляет товары клиенту` поглощается целиком вместе с содержательным текстом.

Решение: добавить реестр защищаемых организаций с ролью `company/counterparty`, полными и краткими именами, алиасами и реквизитами. Приоритетные точные совпадения реестра дополнять контекстными детекторами. Для незнакомой организации явно определить политику: скрывать все, сообщать неопределённость или отклонять отправку. Добавить ОГРНИП, короткие имена и группированные реквизиты; ограничивать адрес и название по структуре поля, а не только длине строки.

Приёмка: на документе с собственной компанией и двумя контрагентами режимы дают ожидаемую разницу; повторное упоминание алиаса собственной компании скрывается без организационно-правовой формы. Профиль ПД продолжает работать независимо от бизнес-режима.

### R07. P1: исходные значения могут попадать в отчёт через исключения

Код: [engine.py:53](../../lightanon/engine.py#L53), аналогичная ветка Polars и `generate_report()`.

Текст исключения без фильтрации попадает в `audit_log`, затем в stdout CLI. Публичный контракт допускает custom rules; правило, бросающее `ValueError('bad value ' + value)`, раскрывает исходную строку в отчёте, хотя выходная колонка успешно зануляется. Это воспроизведено на `review@example.com`.

Решение: в публичном отчёте хранить стабильный код ошибки, класс исключения и идентификатор операции. Сообщение исключения и traceback не включать в стандартный вывод. Для диагностики нужен отдельный явно подключаемый защищённый канал; blacklist регулярных выражений не гарантирует удаление неизвестных секретов.

Приёмка: правило с синтетическим секретом в исключении не оставляет его в audit_log, stdout или stderr штатного запуска; по error code понятно, какая операция не выполнена.

### R08. P1: совпадение путей CLI уничтожает vault

Код: [cli.py:289](../../lightanon/cli.py#L289), [cli.py:293](../../lightanon/cli.py#L293), [cli.py:102](../../lightanon/cli.py#L102).

CLI не проверяет, что input, output, vault и scope являются разными файлами. При `rag sanitize input.txt vault.json --vault vault.json` сначала создаются маппинги, затем файл vault заменяется очищенным текстом. Воспроизведение закончилось невозможностью открыть vault. Совпадение scope с vault имеет аналогичный результат.

Решение: до чтения/записи разрешать абсолютные пути и проверять совпадения, включая существующие симлинки и hard links через `samefile`. Для RAG запретить пересечение всех служебных файлов и input/output; результат и scope писать атомарно. In-place режим, если понадобится, выделить отдельно.

Приёмка: совпадающие пути и алиасы отклоняются до изменений; ранее существовавшие файлы остаются побайтово неизменными.

### R09. P2: ошибка выполнения Polars не отражается в аудите и не обрабатывается как ошибка колонки

Код: [engine.py:75](../../lightanon/engine.py#L75), [engine.py:98](../../lightanon/engine.py#L98).

`try` охватывает создание выражения. Вычисление происходит позднее в `with_columns()` вне обработчика. Успех записывается заранее. Custom rule, возвращающее `pl.col(name).cast(pl.Int64)` для строки email, даёт `InvalidOperationError`, а audit_log всё ещё содержит `Success`. Сырой DataFrame при этом не возвращается; дефект касается ложного аудита и нарушенного контракта fail-closed.

Решение: фиксировать успех после материализации результата. Простой корректный вариант: вычислять результат каждого правила против исходного DataFrame в собственном `try`, проверять форму и добавлять готовую Series в результат; ошибочную колонку заполнять null. Если выбран режим остановки всей операции, явно оформить его одинаково для pandas и Polars.

Приёмка: ошибка как создания, так и выполнения выражения записывается корректно; ни одна не оставляет ложного Success. Текущий тест проверяет только неподдерживаемый `apply_polars`, поэтому нужен отдельный runtime-тест.

### R10. P2: save допускает противоречивые прямые и обратные маппинги

Код: [vault.py:99](../../lightanon/rag/vault.py#L99), [vault.py:208](../../lightanon/rag/vault.py#L208), [vault.py:310](../../lightanon/rag/vault.py#L310).

После `save(token, 'old@example.com')` и `save(token, 'new@example.com')` поиск старого значения возвращает этот же token, который восстанавливается уже в новое значение. Прямое и обратное отображения расходятся. Legacy-loader также не сверяет согласованность двух переданных отображений. Проверка коллизии в sanitizer не защищает публичный `save` и конкурентный get/save.

Решение: сделать маппинги неизменяемыми: повтор точной пары допустим, другая пара с занятым ключом вызывает `MappingConflict`. Проверка и сохранение атомарны на уровне backend. Обратный индекс строить из единственного источника истины; дубли, противоречия и некорректные timestamps отклонять при загрузке. После изменения ключа дедупликации учитывать R04.

Приёмка: конфликт не меняет ни один индекс; точный повтор идемпотентен; повреждённый legacy-файл не принимается молча.

### R11. P2: document/metadata API не возвращает scope для обратного преобразования

Код: [sanitizer.py:285](../../lightanon/rag/sanitizer.py#L285), [sanitizer.py:311](../../lightanon/rag/sanitizer.py#L311); [tests/test_rag.py:12](../../tests/test_rag.py#L12).

Восстановление требует scope, но `sanitize_document()` и `sanitize_metadata()` его теряют. Тесты обходят пробел своим `_token_scope`, который извлекает токены из `str(value)`. Пользователю приходится вручную собирать разрешения, рискуя авторизовать токены, уже присутствовавшие во входе.

Решение: добавить `sanitize_document_with_scope()` и `sanitize_metadata_with_scope()` с общим аккумулятором только фактически выполненных замен. Для документов допустим небольшой result-объект: `text`, `metadata`, `token_scope`. Общий счётчик восстановления должен сохраняться для всего документа.

Приёмка: текст + вложенные metadata проходят полный round-trip через публичный API; вставленный во вход чужой токен не попадает в scope; общее число восстановлений не превышает число замен.

### R12. P2: допустимое имя custom rule создаёт токен, который нельзя восстановить

Код: [sanitizer.py:170](../../lightanon/rag/sanitizer.py#L170), [sanitizer.py:9](../../lightanon/rag/sanitizer.py#L9), [sanitizer.py:412](../../lightanon/rag/sanitizer.py#L412).

Имена `1CLIENT` и `123` проходят нормализацию и успешно скрывают значение. Однако TOKEN_PATTERN требует первую букву; восстановление с автоматически возвращённым scope падает с `ValueError: token_scope contains an invalid token`. Режим mask также не распознаёт такой токен.

Решение: единая грамматика типа сущности для регистрации правила, генерации, парсинга и загрузки vault. Проще отклонять имена без начальной латинской буквы при создании sanitizer/add_rule до обработки данных. Regex custom rule компилировать и валидировать в тот же момент.

Приёмка: недопустимые имена отклоняются заранее; каждое допустимое имя поддерживает sanitize, mask и restore.

### R13. P2: релизные примеры и версия не отражают несовместимые изменения

Код: [rag-demo.py:27](../../rag-demo.py#L27), [setup.py:5](../../setup.py#L5), [docs/ru/rag.md:122](../ru/rag.md#L122), [docs/ru/api.md:163](../ru/api.md#L163); аналогичные разделы EN.

`rag-demo.py` вызывает `deanonymize()` без restore policy/scope и затем проверяет возврат ФИО. Скрипт действительно падает. Документация называет `restored_text` результат, который теперь содержит маски; API-документ дважды описывает FileVault с разными сигнатурами. Версия пакета остаётся `0.2.0`, хотя обязательный salt, переход SHA-256 -> HMAC и новый контракт восстановления меняют поведение приложений и сохранённые псевдонимы. В git нет конфигурации CI; зелёные unit-тесты не обнаружили неработающий пример.

Решение: подготовить следующую версию, например `0.3.0`, и migration guide. Явно указать, что HMAC-значения отличаются от прежних хешей и требуют согласованной миграции JOIN-ключей. Исправить примеры scope/encryption, включить их в smoke-проверки. Добавить сборку wheel/sdist и установку wheel в чистом окружении, исключить `tests` из `find_packages`, убрать placeholder author. Матрицу Python/зависимостей согласовать с реально заявленной поддержкой.

Приёмка: каждый опубликованный пример работает; примеры и версия соответствуют API; smoke запускается из установленного wheel вне checkout. Совместимость Python >=3.9 подтверждается CI либо нижняя граница обновляется по результатам проверки.

## Границы продукта, которые нужно зафиксировать

Эти пункты не следует выдавать за доказанные обходы при любом использовании. Они важны для корректного интеграционного контракта.

1. Scope является доверенной настройкой приложения. Он не подписан и не привязан к tenant/request; каждый вызов восстановления копирует счётчики заново. Повторный вызов с тем же scope снова раскрывает значения. Это ограничитель одного вызова, а не одноразовое разрешение и не полная защита от prompt injection. Модель всё ещё может перечислить по одному экземпляру всех разрешённых токенов. Хранить scope на сервере; если он пересекает границу доверия, выдавать непрозрачный идентификатор серверного контекста с tenant, policy и TTL. Подпись/одноразовое потребление добавлять только под соответствующий сценарий.
2. Metadata API по документации обрабатывает только строковые значения. `{'inn': 123456789012, 'review@example.com': 'author'}` сохраняется открытым: числа и ключи не проверяются. Нужна схема полей metadata с явными правилами и разрешёнными полями для отправки. Известные поля идентификаторов обрабатывать независимо от исходного Python-типа; произвольные числа не превращать все подряд в ПД.
3. `GaussianNoise` не принимает отрицательные значения из-за отрицательного scale; в batch это затирает колонку, в StreamEngine прерывает обработку. `TopCodingFixed` не поддерживает batch, большинство правил не поддерживает Polars. Зафиксировать таблицу возможностей и валидировать схему для выбранного backend до обработки. Для отрицательных сумм можно использовать `abs(value) * std`, а `std`, `step`, quantile и шум проверять на допустимый диапазон и конечность.
4. При больших объёмах FileVault сериализует всё хранилище после каждого нового значения, а `_find_entities` линейно проверяет пересечения со всеми найденными spans. Масштабирование требует замеров и пакетной транзакции записи. Не заявлять высокую пропускную способность без benchmark на целевой нагрузке.

## Уточнённый план реализации

План разделён на пять волн. Каждая волна заканчивается отдельным коммитом, полным регрессом и обновлением RU/EN-документации. Следующую волну начинать только после выполнения критериев предыдущей: это особенно важно для FileVault, где независимые патчи шифрования, блокировок и индексов могут создать несовместимые форматы.

### Волна 1. Безопасное завершение CLI и Engine

Закрывает R01, R07, R08 и R09. Это первый commit, потому что исправления локальны и немедленно исключают прямые утечки через типичные команды.

1. Ввести явный реестр классов правил. `load_schema()` возвращает либо полностью валидированную схему, либо структурированную ошибку; предупреждения с пропуском записей убрать. Проверять имя правила, тип `params` и параметры конструктора до чтения CSV/Parquet.
2. Проверять пути перед любыми записями. Для RAG запретить пересечение `input_file`, `output_file`, `vault` и `scope_file`, включая существующие симлинки; результат и scope писать через временный файл и атомарную замену.
3. Заменить текст исключения в audit_log на безопасные поля: `status="error"`, `error_code`, `exception_type`. Сообщение исключения и traceback оставить только для явно подключаемой приватной диагностики.
4. Для Polars материализовывать каждую колонку внутри собственного обработчика и только затем отмечать `Success`. При runtime-ошибке записывать null-колонку и безопасную ошибку.

Критерии: ошибочная схема, совпадающие пути, runtime-ошибка Polars и custom rule с секретом в исключении не создают или не изменяют output; stdout не содержит входных значений; audit_log не имеет ложного `Success`.

### Волна 2. Новый контракт FileVault

Закрывает R02, R03, R04, R10 и R12. Это одна согласованная миграция формата и API; не следует выпускать её частями.

Целевой контракт:

```python
token = vault.get_token(entity_type="EMAIL", value="user@example.com")
vault.save(token="[EMAIL_...]", entity_type="EMAIL", value="user@example.com")
```

Запись vault становится единственным источником истины: `token`, `entity_type`, `value`, timestamps и версия формата. Обратный индекс `(entity_type, value) -> token` строится и проверяется в памяти, а не принимается как вторая независимая JSON-мапа. Сохранённая пара неизменяема: точный повтор идемпотентен, другое значение для token или другой token для той же пары вызывает `MappingConflict`.

Для файлового backend применить единый lock-файл на весь read-modify-write цикл: загрузка текущего состояния, проверка конфликта, изменение, шифрование и атомарная замена. Нужна кроссплатформенная зависимость с межпроцессной блокировкой либо явно ограниченная поддерживаемая платформа; наиболее практичен небольшой проверенный пакет блокировок, а не собственная реализация `fcntl`.

При заданном ключе vault принимает только версионированный зашифрованный контейнер. Plain JSON в этом режиме отклоняется. Для legacy JSON добавить отдельную CLI-команду миграции с разными source/destination путями, ключом из environment, атомарной записью, повторным чтением результата и явным решением пользователя о последующем удалении исходного файла. Обычный `sanitize` не должен неявно мигрировать или оставлять ощущение, что plaintext уже зашифрован.

Единая грамматика `entity_type`: первая буква `A-Z`, затем `A-Z0-9_`; она применяется при регистрации правил, генерации токена, валидации scope и загрузке vault. Невалидные custom rules отклонять до обработки.

Критерии: невозможно открыть plaintext с ключом; неверный ключ и подмена ciphertext отклоняются; миграция сохраняет все записи; два процесса не теряют добавления и не возвращают удалённые записи; одинаковая строка под EMAIL и PUBLIC получает разные токены; конфликт не меняет хранилище.

Совместимость: это изменение API `BaseVault`, поэтому готовится как версия `0.3.0` с migration guide. Сначала добавить адаптер или ясную ошибку для старого пользовательского vault, затем удалить адаптер только в следующем мажорном релизе.

### Волна 3. Scope, metadata и проверяемое покрытие RAG

Закрывает R05 и R11. После типизации vault можно безопасно расширять публичный RAG API.

1. Добавить `sanitize_metadata_with_scope()` и `sanitize_document_with_scope()`. Scope собирать только из реальных замен; токены, уже присутствовавшие во входном тексте, в него не включать. Для документного результата использовать dataclass или именованный объект с `text`, `metadata`, `token_scope`.
2. Создать версионированный позитивный и негативный корпус RAG в тестах: ФИО с регистром, инициалами и дефисом; паспорт; телефон; СНИЛС; карты 13-19 цифр; ИНН с разделителями; логины с разным регистром; URL, handles и реквизиты. Каждый позитивный пример проверяет не только замену, но и тип токена.
3. Сначала исправить контекстные и span-safe правила: метка телефона до SNILS, метка паспорта до числовых идентификаторов, case-insensitive labels, фамилии с дефисом и инициалы в обоих порядках. Все изменения сопровождаются негативными примерами, чтобы не расширять маскирование произвольного текста.
4. Заменить `residual_risk` на более честный отчёт: отдельные счётчики совпадений, активные правила и `coverage="heuristic"`. Отсутствие совпадений описывать как отсутствие обнаружений, а не как доказательство отсутствия ПД.

Критерии: все R05-примеры скрываются целиком с ожидаемым типом; чужой токен не получает scope; один scope не восстанавливает больше исходного числа замен за одну операцию; отчёт не обещает гарантированную безопасность при нуле совпадений.

Решение о подключении NER отложить до результата корпуса. Если остаются частые пропуски сложных ФИО на целевых документах, добавить NER как опциональный детектор с измеряемыми precision/recall, а не заменять им все правила.

### Волна 4. Контракт корпоративных реквизитов

Закрывает R06. Это функциональное уточнение, которое требует конфигурации пользователя: по одному тексту библиотека не может достоверно определить, какая организация является собственной.

Добавить `OrganizationProfile` с ролью `company` или `counterparty`, полным названием, сокращениями, алиасами и реквизитами. `TextSanitizer` принимает список таких профилей. Режим `company` скрывает только профиль собственной организации; `company_and_counterparties` скрывает оба набора. Для незнакомых организаций ввести явную настройку `unknown_organization_policy`: `report`, `mask`, `reject`. Без profile режимы не должны заявлять разделение ролей; текущие общие regex оставить временно совместимым режимом с предупреждением и запланированным удалением.

Детекторы дополнить ОГРНИП, короткими именами и пробельными вариантами реквизитов. Паттерны названий ограничить до фактического имени, не поглощая свободный текст документа. Адреса скрывать по структурным компонентам, а не только по длине строки.

Критерии: документ с собственной компанией и двумя контрагентами демонстрирует разницу режимов; алиас повторно скрывается; неизвестная организация обрабатывается по явной политике; профиль ПД работает независимо от профиля организаций.

### Волна 5. Релизная подготовка и эксплуатационные границы

Закрывает R13 и фиксирует оставшиеся границы продукта.

1. Исправить `rag-demo.py`, примеры документации и дубли описания FileVault. Демонстрация должна использовать `sanitize_with_scope()` и явный `restore`.
2. Выпустить `0.3.0`, описать несовместимости: обязательный secret salt, HMAC вместо прежнего SHA-256, scope для восстановления и новый vault API/миграция. Версию не повышать до закрытия волн 1-4.
3. Добавить CI: тесты, запуск демо, build wheel/sdist, установка wheel в чистом окружении и smoke CLI. Исключить `tests` из распространяемых пакетов, заполнить метаданные автора/лицензии и подтвердить поддерживаемые версии Python.
4. В документации зафиксировать границы: scope является серверным контекстом, не одноразовым разрешением; metadata без схемы не обрабатывает числовые значения и ключи; FileVault предназначен для небольших локальных задач; для сервиса нужен транзакционный backend; возможности pandas, Polars и StreamEngine публикуются как отдельная таблица.

Критерии: все примеры запускаются из установленного wheel; migration guide покрывает переход с `0.2.0`; CI повторяет релизные проверки; публичная документация не обещает функциональность, которой библиотека не предоставляет.

## Проверки, которых не хватает перед релизом

- CLI: частично ошибочная схема, пустой конфиг, неверный тип params, совпадение путей и отсутствие изменений при отказе.
- Engine: runtime-ошибка Polars и исключение с исходным значением в тексте.
- Vault: JSON вместо ciphertext, повреждённый/пустой файл, неверные даты, миграция, устаревшие экземпляры, конфликт пары и конкурентное удаление.
- RAG: межтиповая дедупликация, невалидное имя правила, document scope, входные токены, лимит на весь документ.
- Детекторы: регистр, инициалы, составные фамилии, разные длины карт, контекст числового идентификатора, алиасы компаний и отрицательные примеры.
- Доставка: демо, импорт и CLI из wheel, совместимость поддерживаемых Python/ОС и крайних версий зависимостей.

Релиз можно считать готовым после закрытия P1, исправления P2 в поддерживаемых сценариях и проверки артефакта установки. Число прошедших тестов само по себе не заменяет эти критерии. После исправлений нужно повторить именно приведённые воспроизведения на новом commit и зафиксировать результат для каждого R01-R13.
